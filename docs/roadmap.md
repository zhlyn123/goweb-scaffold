# Go Web Scaffold 计划周期表

## 1. 计划说明

本计划面向一个生产级 Go Web 脚手架，目标是在保证可学习、可运行的前提下，逐步沉淀高可用、低耦合、可复用的工程能力。

建议周期：8 周。

建议节奏：

- 每周完成一个明确阶段。
- 每个阶段都保证代码可运行。
- 优先交付核心闭环，再补充高级能力。
- 每周都保留测试、文档和复盘时间。

## 2. 总体阶段

| 周期 | 阶段 | 核心目标 | 交付结果 |
|---|---|---|---|
| 第 1 周 | 架构骨架 | 建立项目结构和启动流程 | 服务可启动，目录规范确定 |
| 第 2 周 | 基础设施 | 配置、日志、HTTP、中间件 | 基础 API 服务可用 |
| 第 3 周 | 数据层 | PostgreSQL、GORM、Migration | 数据库访问闭环 |
| 第 4 周 | 用户与认证 | 用户、登录、JWT | 用户认证闭环 |
| 第 5 周 | 权限与安全 | RBAC、限流、安全中间件 | 基础权限体系可用 |
| 第 6 周 | 可观测性 | Metrics、Tracing、健康检查 | 服务可监控、可排障 |
| 第 7 周 | 工程化 | Docker、测试、Makefile、文档 | 本地环境标准化 |
| 第 8 周 | 稳定化 | 重构、补测、示例完善 | 可作为 v0.1.0 使用 |

## 3. 第 1 周：架构骨架

### 目标

建立脚手架基础结构，明确分层边界和依赖规则。

### 工作内容

- 初始化 Go module。
- 创建 `cmd/api` 入口。
- 创建 `internal/app` 应用装配层。
- 创建 `internal/modules` 模块目录。
- 创建 `internal/platform` 平台能力目录。
- 创建 `internal/shared` 共享能力目录。
- 定义基础启动流程。
- 编写架构约束说明。

### 交付物

- 项目目录结构。
- 应用入口 `main.go`。
- 基础 bootstrap 流程。
- 架构设计文档。

### 验收标准

- `go run ./cmd/api` 可以执行。
- 目录结构符合架构设计。
- 没有业务代码污染平台层。

## 4. 第 2 周：基础设施

### 目标

完成 API 服务运行所需的基础能力。

### 工作内容

- 实现配置加载。
- 实现 zap 日志初始化。
- 实现 Gin HTTP Server 封装。
- 实现统一响应结构。
- 实现统一错误结构。
- 实现 request id 中间件。
- 实现 recovery 中间件。
- 实现 access log 中间件。
- 实现 CORS 基础配置。

### 交付物

- 配置模块。
- 日志模块。
- HTTP Server 模块。
- 通用中间件。
- `/health/live` 接口。

### 验收标准

- 服务可读取配置启动。
- 请求日志包含 method、path、status、latency、request_id。
- panic 可以被 recovery 捕获。
- API 响应格式统一。

## 5. 第 3 周：数据层

### 目标

建立稳定的数据访问基础。

### 工作内容

- 接入 PostgreSQL。
- 封装数据库连接池。
- 接入 GORM。
- 接入 goose migration。
- 建立 migration 目录规范。
- 定义事务管理器接口。
- 实现 Repository 基础示例。

### 交付物

- 数据库配置。
- PostgreSQL 连接。
- migration 命令。
- 事务管理器雏形。
- 示例数据表。

### 验收标准

- 应用启动时可连接数据库。
- migration 可以执行 up/down。
- Repository 不暴露 GORM 给 application 层。
- 数据库配置可通过环境变量覆盖。

## 6. 第 4 周：用户与认证

### 目标

完成用户登录认证闭环。

### 工作内容

- 建立 user 模块。
- 建立 auth 模块。
- 实现用户注册。
- 实现密码 bcrypt 加密。
- 实现用户登录。
- 实现 JWT 签发。
- 实现 JWT 鉴权中间件。
- 实现获取当前用户接口。

### 交付物

- 用户表 migration。
- 用户 domain entity。
- 用户 repository 接口和实现。
- auth usecase。
- 登录接口。
- 当前用户接口。

### 验收标准

- 用户可以注册。
- 密码不明文存储。
- 用户可以登录并获得 token。
- 受保护接口无 token 不能访问。
- application 层不依赖 Gin 和 GORM。

## 7. 第 5 周：权限与安全

### 目标

完成基础权限模型和安全防护。

### 工作内容

- 建立 RBAC 基础表结构。
- 实现角色模型。
- 实现权限模型。
- 实现用户角色绑定。
- 实现权限校验中间件。
- 实现登录接口限流。
- 实现请求体大小限制。
- 补充 CORS 安全配置。

### 交付物

- RBAC migration。
- RBAC domain 模型。
- 权限校验中间件。
- 限流中间件。
- 安全配置项。

### 验收标准

- 可以给用户绑定角色。
- 可以根据权限保护接口。
- 登录接口具备基础限流。
- 安全配置可通过配置文件调整。

## 8. 第 6 周：可观测性

### 目标

让服务具备可监控、可排障能力。

### 工作内容

- 接入 Prometheus metrics。
- 暴露 `/metrics`。
- 统计 HTTP 请求总数。
- 统计 HTTP 请求耗时。
- 统计 HTTP 状态码。
- 接入 OpenTelemetry tracing。
- 日志注入 trace_id。
- 实现 `/health/ready`。
- ready 检查数据库和 Redis。

### 交付物

- metrics 模块。
- telemetry 模块。
- 健康检查模块。
- Prometheus 示例配置。

### 验收标准

- `/metrics` 可被 Prometheus 抓取。
- 请求日志包含 request_id 和 trace_id。
- `/health/ready` 能反映依赖状态。
- 数据库或 Redis 不可用时 ready 返回失败。

### 工作内容

- 集成 Redis 容器。
- 编写 Makefile。
- 编写基础单元测试。
- 编写 Repository 集成测试。

- 生成 Swagger / OpenAPI 文档。

### 交付物

- docker-compose.yml。
- Makefile。

### 验收标准

- `make test` 可以执行测试。
- API 文档可以访问或生成。

## 13. 风险与控制

| 风险 | 表现 | 控制方式 |
|---|---|---|
| 设计过重 | 目录很多但功能跑不通 | 每周必须有可运行交付 |
| 抽象过度 | 接口太多，开发困难 | 接口只围绕真实替换点设计 |
| 学习成本高 | 不知道代码该放哪里 | 编写模块开发指南和示例模块 |
| 高可用空泛 | 只有口号没有实现 | 以健康检查、超时、日志、指标作为验收 |
| 业务耦合 | handler 直接写数据库 | 明确依赖规则并在评审中检查 |

## 14. v0.1.0 完成定义

当以下内容全部完成，可以发布 `v0.1.0`：

- 服务可通过 Docker Compose 一键启动。
- 用户注册、登录、当前用户接口可用。
- JWT 鉴权可用。
- PostgreSQL migration 可用。
- Redis 连接和基础封装可用。
- 统一响应和统一错误可用。
- 日志、request id、recovery 可用。
- `/health/live`、`/health/ready`、`/metrics` 可用。
- README 包含启动、配置、开发说明。
- 至少包含 user 模块作为标准模块示例。
